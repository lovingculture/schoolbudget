# 결산자료 XLS/XLSX 호환성 개선 설계

## 목표

에듀파인 `세입세출결산총괄표`의 실제 `.xls`와 `.xlsx`를 동일한 결과로 처리한다. 파일 확장자를 바꾸거나 오류를 숨기지 않고 내부 파일 형식, 시트 구조, 표 제목과 셀 값을 검증하며 기존 `.xls` 동작을 유지한다.

이번 설계의 범위는 가장 시급한 결산자료 업로드 오류 수정이다. HWPX 다운로드, 추경 대시보드, PDF 목차, 성립전예산, 3개년 추경 시뮬레이션과 본예산 통합 기능은 각각 별도 설계와 구현계획으로 진행한다.

## 확인된 원인

- 정상 표본 `세입세출결산총괄표.xls`는 OLE2/BIFF 형식이며 금액 셀이 숫자형이다.
- 실패 표본 `세입세출결산총괄표.xlsx`는 정상 OOXML ZIP 형식이다.
- 두 표본의 시트명은 `세입세출결산총괄표`로 같고, 표 제목·헤더·병합셀·금액도 일치한다.
- 실패 `.xlsx`는 금액을 `"361,675,980"`과 같은 쉼표 포함 문자열로 저장한다.
- 현재 총액 파싱은 `asNumber`를 사용하므로 문자열 금액도 처리하지만, 세입·세출 상세행은 `typeof amountValue !== "number"`인 행을 버린다.
- 이 때문에 `.xlsx`의 세입 6건과 세출 7건이 모두 제외되고 `세입 결산내역을 읽을 수 없습니다.` 오류가 발생한다.

## 권장 접근

파서 입구에서 파일의 실제 형식을 확인하고, 표 구조 탐색과 셀 값 변환을 분리한다. 상세행 금액도 총액과 동일한 숫자 정규화 함수를 사용하되, 공백이나 임의 문자열을 0원으로 조용히 바꾸지 않고 유효성 결과를 명시적으로 반환한다.

SheetJS 옵션만 변경하는 방식은 파일별 저장형식 차이를 안정적으로 해소하지 못한다. 브라우저에서 파일을 다시 변환하는 방식도 서식과 수식 결과가 달라질 수 있으므로 사용하지 않는다.

## 구성요소

### 1. 파일 형식 검사

`src/features/closing/parser.ts`에서 입력 바이트의 시그니처를 검사한다.

- OLE2/BIFF: `D0 CF 11 E0 A1 B1 1A E1`
- OOXML ZIP: `50 4B`
- 그 외 형식은 `파일 확장자는 엑셀이지만 실제 파일 형식이 올바르지 않습니다.`로 거절한다.

확장자 검사는 화면의 빠른 안내 용도로 유지하되 최종 판정은 바이트와 워크북 구조를 기준으로 한다.

### 2. 금액 정규화

파서 내부에 `parseMoneyCell(value)`를 둔다.

- 유한한 숫자: 그대로 허용
- 쉼표와 주변 공백이 포함된 정수 문자열: 쉼표 제거 후 허용
- 음수 문자열: 허용
- 빈 값: `missing`
- 숫자가 아닌 문자열, `NaN`, 무한대: `invalid`

반환값은 성공 여부와 숫자를 구분하는 판별 가능한 타입으로 만들어 `0원`과 `변환 실패`가 섞이지 않게 한다.

### 3. 워크북·시트·표 탐색

- 숨김 여부와 관계없이 시트 이름과 표 제목을 함께 검색한다.
- 시트명이 정확히 일치하면 우선 사용한다.
- 시트명이 달라도 `YYYY년도 학교회계 결산총괄표` 제목과 필수 표 헤더를 모두 갖춘 시트는 후보로 인정한다.
- 후보가 없거나 둘 이상이면 사용자가 이해할 수 있는 오류를 표시한다.
- 병합셀은 SheetJS가 제공하는 좌상단 값을 기준으로 읽고, 현재 행/열 위치 탐색을 유지한다.

### 4. 상세행 파싱

- 세입: `장`, `관`, 같은 행의 `결산액` 열을 탐색한다.
- 병합된 `장` 값은 다음 장 값이 나타날 때까지 상속한다.
- 세출: `정책사업`과 같은 행의 `결산액` 열을 탐색한다.
- 상세 금액은 `parseMoneyCell`을 거쳐 숫자형과 문자열형을 동일하게 처리한다.
- 금액이 없는 빈 행은 건너뛰고, 사업명이 있는데 금액이 잘못된 행은 행 번호와 함께 오류로 보고한다.
- 합계행에서 상세 탐색을 종료한다.

### 5. 오류 안내

오류를 다음 단계로 구분한다.

1. 실제 엑셀 형식이 아님
2. 워크북을 열 수 없음
3. 결산총괄표 시트를 찾지 못함
4. 필수 제목 또는 헤더 누락
5. 금액 셀 변환 실패
6. 처리할 상세행 없음

사용자 메시지에는 실패 단계, 문제가 된 항목과 가능한 경우 엑셀 행 번호를 포함한다. 내부 예외나 스택 추적은 화면에 노출하지 않는다.

## 데이터 흐름

1. 사용자가 `.xls` 또는 `.xlsx`를 선택한다.
2. `ClosingPage`가 바이트를 `parseClosingWorkbook`에 전달한다.
3. 파서가 실제 형식과 워크북 열기를 검증한다.
4. 결산총괄표 후보 시트를 찾는다.
5. 총액, 잉여금, 세입 상세, 세출 상세를 정규화해 추출한다.
6. 합계 관계와 상세 합계를 검증한다.
7. 성공 시 기존 `ClosingSource`를 반환해 편집·미리보기·다운로드 흐름을 그대로 사용한다.
8. 실패 시 `ClosingParseError`의 사용자용 메시지를 표시한다.

## 하위 호환성

- `ClosingSource`의 공개 구조는 변경하지 않는다.
- 기존 `.xls` 표본의 학년도, 학교명, 총액, 잉여금, 세입 6건과 세출 7건 결과가 유지되어야 한다.
- 예산 안건설명서, 102-2 집행실적, 성립전예산 파서는 변경하지 않는다.
- 파일은 브라우저 메모리에서만 처리하며 서버로 전송하지 않는다.

## 테스트 전략

### 파서 단위 테스트

- 실제 정상 `.xls`가 기존 결과를 반환한다.
- 실제 실패 `.xlsx`가 `.xls`와 같은 총액과 상세행을 반환한다.
- 숫자형, 쉼표 문자열, 음수 문자열과 0원을 구분해 처리한다.
- 숫자가 아닌 금액 문자열은 행 번호가 포함된 오류를 낸다.
- 잘못된 확장자와 실제 형식 불일치를 거절한다.
- 시트명이 달라도 제목과 필수 헤더가 정확하면 탐색한다.
- 제목 또는 필수 헤더가 없는 파일은 구체적인 메시지로 거절한다.

### 화면 테스트

- `.xls`와 `.xlsx` 선택 시 모두 결산 편집 화면으로 전환된다.
- 잘못된 파일은 오류 안내를 표시하고 이전 결과를 남기지 않는다.
- 다른 파일 선택 후 재업로드가 가능하다.

### 회귀 검증

- 전체 Vitest 실행
- TypeScript/Vite 프로덕션 빌드
- 실제 `.xls`, `.xlsx`, 잘못된 파일을 이용한 브라우저 업로드
- 두 정상 파일의 총액, 상세행 개수와 생성 결과 비교

## 배포 원칙

- 수정은 별도 `codex/` 브랜치에서 진행한다.
- 테스트가 통과하면 Vercel Preview에만 배포한다.
- Preview 주소와 테스트 결과를 사용자에게 제공한다.
- 사용자 최종 승인 전에는 Production 배포, Promote 또는 운영 도메인 변경을 하지 않는다.

## 후속 기능 경계

이번 수정에서 공통 숫자 정규화와 오류 모델은 결산 파서 내부에만 적용한다. 향후 102-2, 성립전예산과 본예산 파서에 재사용할 필요가 확인되면 별도 공통 모듈 설계를 거쳐 이동한다. 지금 바로 전역 파서 프레임워크로 확장하지 않아 회귀 위험을 제한한다.
